# Brief: translate one area of the site

The site (Next.js 16, App Router) now serves every page under `src/app/[locale]/` with next-intl: English at the bare path, `/it`, `/tr`, `/es`, `/pl` prefixed. Read first:
- `src/i18n/locales.ts`, `src/i18n/routing.ts`, `src/i18n/navigation.ts`, `src/i18n/request.ts`, `src/i18n/alternates.ts`, `src/i18n/namespaces.ts`
- The finished pattern: `src/components/site/site-header.tsx` (server, `getTranslations`), `src/components/site/mobile-menu.tsx` (client, `useTranslations`), `src/components/site/editorial-line.tsx` (rich text with a link via `t.rich`), `src/components/site/site-footer.tsx`, and `messages/en/common.json` with its it/tr/es/pl siblings.
- `tests/unit/i18n-catalogues.test.ts`: every locale must have exactly the English keys, the same ICU placeholders `{name}` and tags `<link>`, nothing empty.

Your job, for the files and namespace(s) assigned to you:
1. Move EVERY user-facing English string into `messages/en/<namespace>.json` (nested keys by page/component), including: visible text, button labels, aria-labels, alt text, titles, placeholders, error/notice messages, page `<title>`/description metadata, and strings produced by the `src/lib/...` modules assigned to you that end up on screen. Use ICU syntax for variables and plurals (`{count, plural, one {# question} other {# questions}}`) instead of string concatenation; use `t.rich` for embedded links/emphasis. Never translate: exam names and brand names (Examer, SAT, TOLC-E, IMAT, Bocconi...), question/answer content, and text that comes from exam configs or research records (official facts quoted from the test maker stay as published). Where such English text appears inside a translated page, leave it as data.
2. Server components: `const t = await getTranslations('<ns>')`; client components: `useTranslations('<ns>')`. Pages with `generateMetadata`: take `params` (it now includes `locale`), translate title/description, and set `alternates: languageAlternates('<english path>', locale)` (keep any existing canonical logic consistent with it). Numbers and dates: format with next-intl's `useFormatter`/`getFormatter` or `Intl` with the active locale instead of hard-coded `en-GB`/`en-US`.
3. Lib functions that return English sentences: prefer returning a message key plus params (and translate at the render site), or accept a translator `t` argument. Keep their tests passing; update tests that assert English text so they still assert English (render with locale `en`; `tests/unit/helpers/intl.ts` has `withIntl()` for client components).
4. Write `messages/it/<ns>.json`, `messages/tr/<ns>.json`, `messages/es/<ns>.json`, `messages/pl/<ns>.json`: complete, natural, fluent translations in the register of a careful education website (Italian: tu form; Spanish: tú, neutral European Spanish; Turkish: siz form; Polish: informal "Ty" form as is usual for consumer sites, consistent with common.json). Keep product terms consistent with `messages/<locale>/common.json` (e.g. nav labels). Keep placeholders/tags exactly. Legal pages: translate fully and add a sentence (in each language) that the English version prevails in case of discrepancy.
5. Links and redirects: use `Link`/`useRouter`/`usePathname` from `@/i18n/navigation` (already swapped in most files); do not hard-code `/en`.
6. Do not edit files outside your assignment, `src/i18n/*`, `messages/*/common.json`, or other namespaces' files. Other agents are converting other areas in parallel. If a shared component you need is outside your list, leave its strings and report it.
7. Verify: `npm run typecheck`, `npx vitest run` (all must pass; the full suite occasionally shows one order-dependent notebook paging failure that passes on re-run — re-run once before concluding), and render-check: `npm run build` is shared by everyone, so do NOT run it; instead rely on typecheck and tests.
8. Do not commit. Report: files changed, namespace key count, anything left in English and why, and test/typecheck output.
